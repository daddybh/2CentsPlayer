# 探索电台推荐策略 MVP 设计

## 目标

把探索电台从“随机选收藏种子 + 单路相似召回 + AI 重试”改为稳定、可解释、首播不依赖 AI 的推荐链路。MVP 优先改善首批歌曲命中率、连续跳过率、重复度和补歌稳定性，不引入向量数据库或服务端用户画像。

## 范围

### 包含

- 修正正反馈歌手被长期排除的问题。
- 用确定性、多样化的种子选择替代随机种子。
- 从多个兴趣种子召回候选并合并去重。
- 为候选增加本地评分，并在评分后做歌手与歌曲多样性编排。
- 把 AI 从首播关键路径移出；AI 仅在本地快速来源低产出时后台补充。
- 候选进入队列前保证身份有效；首曲进入播放器前保证可播放。
- 修复推荐链路现有的 JVM 日志测试失败、空播放地址候选编排和相关回归测试。
- 增加最小诊断摘要，使每次补歌可以看到召回、过滤和入队数量。

### 不包含

- UI 大改。
- 向量模型、云端画像或新的推荐服务。
- AI 密钥加密、全局网络安全配置等独立安全改造。
- 音频缓存、下载和离线播放。

## 方案比较

### 方案 A：继续强化 AI Prompt

改动最少，但一次搜索无法表达多峰兴趣，模型延迟和接口兼容性仍在首播关键路径上，结果也难以复现。不采用。

### 方案 B：完全本地相似推荐

速度快、稳定、容易测试，但候选来源低产出时缺少扩圈能力，长期新鲜度有限。

### 方案 C：多源召回 + 本地评分 + AI 异步补充

本地快速来源负责首批可用候选，统一评分器决定相关性，队列编排器只负责多样性；AI 仅在候选不足时作为补充来源。该方案兼顾稳定性、可解释性和探索能力，作为 MVP 采用。

## 架构

推荐链路拆分为四个明确阶段：

1. `RadioSeedSelector`：从收藏和反馈历史中选择最多 3 个代表性种子。
2. 候选召回：对每个种子请求相似歌曲，合并为候选池。
3. `RadioCandidateScorer`：根据种子顺序、多种子共同命中、正负反馈、最近播放和可播放元数据进行本地评分。
4. `RadioQueueComposer`：按最终分数选歌，并应用歌曲去重、歌手间隔和探索比例约束。

`RadioReplenishmentEngine` 继续负责编排各阶段，但不再让候选来源决定最终队列顺序。快速来源返回不足时才调用 AI；AI 失败不会阻止已获得的本地候选入队。

## 数据模型

### 种子

`RadioSeed` 包含：

- `track`
- `score`
- `reason`：最近收藏、完整播放、重播或长期收藏

种子选择规则：

- 最近明确正反馈优先于普通收藏。
- 同一歌手最多一个种子。
- 最近刚播放或已连续作为种子的歌曲降权。
- 相同输入必须产生相同种子顺序，不使用 `shuffled()`。

当历史不足时，按收藏存储顺序补足；网易云来源优先用于网易云相似接口，但不能挤掉全部其他兴趣簇。

### 候选

`RadioCandidateEvidence` 包含：

- 真实 `Track`
- 命中的种子 ID 集合
- 召回源集合
- 本地分数
- 入队原因

候选身份使用规范化歌曲名、主要歌手和跨来源 ID 共同去重，避免同一歌曲的网易云/酷我版本同时出现。

## 反馈与排除

- `avoidTrackIds` 只包含当前队列、当前会话已播放歌曲和明确负反馈歌曲。
- `avoidArtistKeys` 只用于最近 3 首的短期歌手间隔，不再使用 30 天全部历史歌手。
- 正反馈歌手不进入硬排除集合。
- 明确负反馈歌曲硬过滤；负反馈歌手只降权，不永久过滤。
- 完整播放、重播和收藏提高候选或相邻兴趣种子的权重。
- “收藏后扩圈”只影响下一波推荐，不让整个会话永久处于 `EXPANDING`。

## MVP 评分

评分采用整数以便测试和日志解释：

- 第一种子命中：`+40`
- 第二种子命中：`+30`
- 第三种子命中：`+20`
- 每增加一个不同种子共同命中：`+15`
- 正反馈歌手：`+12`
- 多个召回源共同命中：每个额外来源 `+10`
- 可用来源 ID 和完整元数据：`+5`
- 最近播放过同一歌曲：硬过滤
- 明确负反馈歌曲：硬过滤
- 负反馈歌手：`-25`
- 最近 3 首中出现的歌手：`-20`

分值只决定候选优先级，不直接表达 `SAFE/ADJACENT/SURPRISE`。探索桶由候选与种子的连接强度派生，AI 返回的桶位只作为弱提示。

## 队列编排

- 先按分数降序，再按规范化歌曲键稳定排序，保证可复现。
- 同一歌曲只能出现一次。
- 同一歌手默认间隔至少 3 首；候选不足时允许逐级放宽，不能因此返回空队列。
- 前 3 首只使用有明确种子连接的候选。
- 平衡状态目标为约 70% 熟悉、25% 相邻、5% 探索；MVP 队列较短时允许取整。
- 恢复状态只选熟悉和相邻候选。
- 候选不足时返回已有结果，不因为未达到桶位配额而丢弃高分歌曲。

## 可播放性与降级

- 快速召回阶段不解析所有音频 URL，避免首播等待过长。
- 首曲在提交播放前必须完成 URL 解析；解析失败时依次尝试下一名候选。
- 后续歌曲保留延迟解析，但空 URL 不再被当作“已验证可播放”。
- 快速来源有结果时立即形成队列；不足部分在后台请求 AI。
- AI 缺少配置、超时或返回错误时维持本地队列，不切换到失败状态。

## 诊断

每次补歌输出一个结构化摘要，不在领域类里直接调用 `android.util.Log`：

- 选中的种子及原因
- 每个来源召回数
- 跨来源去重数
- 负反馈、最近播放和歌手间隔过滤数
- 首曲可播放解析尝试数
- 最终入队数及每首歌的分数摘要
- 本地阶段和 AI 补充阶段耗时

通过注入的轻量 Logger 输出，默认测试环境使用空实现，避免 JVM 单测依赖 Android Log。

## 测试

### 单元测试

- 正反馈歌手不会进入长期硬排除集合。
- 最近 3 首歌手会被短期降权或间隔处理。
- 相同收藏和历史始终选择相同种子。
- 多个歌手能分别成为种子。
- 多种子共同召回的候选得分更高。
- 明确负反馈和已播放歌曲被过滤。
- 只有 SAFE 候选时仍能补足队列，不受桶位模板限制。
- 空 URL 候选不会被误判为已验证可播放。
- 快速来源有候选且 AI 未配置时仍能启动电台。
- AI 失败时保留本地候选。

### 回归验证

- `./gradlew testDebugUnitTest`
- `./gradlew assembleDebug`

验收要求是全部单元测试通过，且不通过忽略 Android 未 mock 方法来掩盖问题。

## 成功标准

MVP 代码层面以以下可验证结果为准：

- 相同输入的首批队列可复现。
- 没有 AI 配置也能从收藏启动探索电台。
- 快速来源返回至少一个有效候选时，不因桶位不足而返回空队列。
- 正反馈歌手不会被 30 天历史永久排除。
- 首曲播放地址失败时能尝试下一候选。
- 所有现有与新增单元测试通过。

真实听感的后续基线指标为前 3 首跳过率、完整播放率、首曲准备耗时和重复歌手率；本次 MVP 只完成采集所需的诊断数据，不引入遥测上报。
